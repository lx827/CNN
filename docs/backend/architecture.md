# 后端架构与运行时契约

## 分层与依赖方向

```text
HTTP/WS 路由
  → 业务服务与诊断编排
  → 独立纯数值算法
  → 结构化结果
  → 持久化 / 严格 JSON / WebSocket
```

`cloud/app/algorithms/` 只承担纯计算，不依赖 FastAPI、SQLAlchemy、设备数据库、缓存或全局业务配置。NumPy 到列表、非有限值到 `null`、认证、展示截断和持久化都在业务边界完成。业务服务可以组合算法，但不得在路由包中另藏第二份数学实现。

## 应用生命周期

启动过程初始化数据库和默认设备、设置受控线程池并启动后台分析与离线监测；关闭时取消后台任务并释放执行器。路由模块导入不能替代显式生命周期管理。

数据库初始化采用增量建表、补列和 `checkfirst` 索引创建，不删表或清理历史诊断。代码回退不会自动撤销已建索引。

## 2G 生产红线

- 全局异步计算复用现有线程池，`max_workers=2` 是内存上限，不是可随意提高的性能参数。
- 后台分析由容量 1 的信号量串行，全设备重新诊断逐批执行。
- DataView 实时计算只处理最多 `sample_rate * 5` 个采样；长记录先做业务截断，再执行慢去噪和数值计算。
- 新任务先计算窗口、模态、频谱网格和完整数组的峰值内存，不新增并行算法组合。
- 慢计算通过现有执行器让出事件循环，避免阻塞 HTTP/WebSocket 协程调度。

## 后台分析副作用

后台 worker 扫描未分析批次，执行多通道综合诊断，保存批次与通道结果、更新设备健康和原始数据已分析状态，生成告警并推送 WebSocket。完整 NumPy 结果在入库和推送前统一经过严格 JSON 转换，避免只转换部分通道字段而遗漏批次阶次结果。

算法替身测试只能证明 worker 的事务和序列化，不证明真实诊断准确率。验证入口见 [测试索引](../tests/INDEX.md)。

## 表示与展示边界

- 完整有效频谱先用于指标和评估，再做频率/倒频率展示截断。
- 绘图极值抽点只压缩显示，不改变原始波形、完整分析数组或诊断输入。
- DC24 counts 显示分析与机械设备诊断分离；未标定 counts 不进入健康评分。
- `indeterminate`、`not_evaluable` 和缺失值不得被 JSON 适配转换成健康或有效阴性。
