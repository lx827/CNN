# 持久化契约

本页记录业务持久化语义；ORM 字段类型和约束以 `cloud/app/models.py` 为准，外部请求/响应以 [API 文档](../api/backend_api.md) 和 OpenAPI 为准。

## 表与所有权

| 表 | 稳定内容 |
|----|----------|
| `devices` | 设备编号、名称/位置、通道数与名称、采样率、窗口、健康状态、运行/上传/轮询配置、告警阈值、齿轮与轴承参数、压缩/降采样和在线状态 |
| `sensor_data` | 设备、批次、通道、原始波形、采样率、是否已分析、是否特殊采集、分析与创建时间 |
| `diagnosis` | 设备/批次/通道、健康分、故障概率、IMF 能量、阶次结果、转频、状态、Engine 结果、完整通道分析、去噪方法和分析时间 |
| `alarms` | 设备、级别、类别、通道、标题/描述/建议、批次、处理状态与时间 |
| `collection_tasks` | 设备、任务状态、采样率、时长、起止时间、结果批次和错误信息 |

原始波形与分析结果分开：重新诊断更新诊断记录，不重写原始采样。设备机械参数属于业务配置，纯算法层只接收已验证的结构化参数。

## 批次保留

- 普通 `sensor_data` 批次按 1–16 循环覆盖。
- `batch_index >= 101` 的特殊/永久批次不按普通循环清理。
- 删除与保留必须以实际服务逻辑为准，不仅凭 `is_special` 名称推断。

## 诊断历史与缓存

诊断缓存键为 `(device_id, batch_index, channel, denoise_method)`。索引用于设备摘要、批次摘要和通道去噪缓存检索；不增加唯一约束，也不清理旧记录。

最新记录规则：

1. 有效 `analyzed_at` 晚于空时间。
2. 首先按 `analyzed_at` 降序。
3. 同时间按 `id` 降序。
4. 列表读模型只选摘要字段，避免加载历史大 JSON。

通道缓存更新必须保护其他去噪结果；独立数值查询没有既有诊断时不得创建伪健康记录。

执行去噪失败的通道可以持久化未知健康分（JSON `null`）、`indeterminate` 与方法/原因。该记录表示本次分析失败，不能补成正常分数，也不能因此抹掉其他通道的合法分析。它仍遵守既有最新记录与缓存键，不改变表结构或批次保留规则。

## 初始化与增量迁移

启动时创建缺失表、补齐既有数据库新增列，并以 `checkfirst` 创建缺失索引。已存在表的索引需要显式补建，因为单纯 `create_all` 不会完成该操作。迁移可重复执行，不删表、不修改既有诊断语义；首次建索引可能增加启动耗时。

数据库会话由请求或 worker 边界管理。摘要查询不提交或关闭调用方 Session；后台分析的事务、原始数据已分析标记、设备健康和告警输入需要一致提交。

## JSON 大字段

`order_analysis`、`engine_result` 和 `full_analysis` 可包含大型 NumPy 派生结构。入库前统一严格 JSON 转换，非有限值按约定转为 `null`。列表页面不得为摘要而读取这些字段；需要完整结果时通过专门诊断查询读取。
