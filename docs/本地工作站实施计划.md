# 本地工作站实施计划

- 状态：T1～T5 已实施；T6 自动回归已完成本轮覆盖，Rust Windows 实机验收未完成
- 日期：2026-11-15
- 架构决策：[ADR 0011](adr/0011-shared-cloud-local-workstation.md)

## 1. 目标与现状

目标是在直连 DC24 的 Windows 电脑上完成采集、保存、诊断和网页查看，断网及云服务器不可用时仍能完整运行。云端与本地工作站以后只修改同一份后端和前端代码。

现状不是从零开始：

- [一键启动器](../scripts/dc24_start.py)已经启动本机完整后端、同一前端构建产物和 DC24 采集进程。
- [DC24 实时保存](../collector/dc24_live.py)将四路有符号 24 位 counts 以 int32 写入 `counts.i32`，CSV 同样保存整数。
- [counts 显示分析](../server/app/services/acquisition_analysis.py)在计算时逐通道转换为 float64，但明确不作机械故障判定。
- [通用诊断入口](../server/app/services/diagnosis/ensemble.py)将输入转为 float64，默认最多取 5 秒，没有统一 z-score 或 min-max 归一化；具体算法内部的处理不属于全链路归一化。
- DC24 的 `acquisition_jobs` 已接入通用 `sensor_data → analyzer → diagnosis`，本地单次与流式记录都直接登记用户目录中的原始 counts。

## 2. 已确认边界

| 项目 | 决策 |
|------|------|
| 应用代码 | 后端、算法、API、数据库模型和前端均只有一份 |
| 本地运行 | 互联网和云端不可用时，采集、保存、诊断、历史查看均可用 |
| 数据归属 | 本地与云端各自保存数据，不自动同步 |
| 原始波形 | 本地只保留用户选择目录中的原始文件，不再制作本机后端副本或浮点副本 |
| 分析输入 | 直接读取原始文件的时间段，在内存中转 float64，不增加全链路归一化 |
| 长记录 | 默认按 5 秒一段自动分析；窗口长度进入统一配置，不写死在业务流程中 |
| 分析执行 | 沿用现有串行分析约束，先完成的窗口可以先查看 |
| 通道 | 硬件帧保存四路；每路独立启停显示和诊断，至少一路有效即可分析 |
| 异常通道 | 用户手动停用；原始数据仍保留，可重新启用并重新分析 |
| 整卡断线 | 属于整个采集链路中断，不伪造其余通道继续采样 |
| 历史页面 | 沿用现有 DataView、Diagnosis、Alarm 和参数查看，不新增本地历史页面 |
| 本地认证 | 页面免登录，后端只监听 `127.0.0.1`；云端认证不变 |
| 初始化 | 本地只使用实际采集对象，不创建云端十个演示设备 |
| 驱动 | Python TCP 默认，Rust FFI 可选，原厂 DLL 可选保留 |
| 交付 | 源码目录、锁文件、前端构建产物、uv 依赖组和一键启动；暂不做安装包或 EXE |

本次不做 counts 工程单位转换、自动传感器故障判断、实时连续机械评分、云端数据同步或新的本地历史页面。

## 3. 目标数据流

```text
DC24 四路硬件
→ 独立采集进程
→ Python / Rust / 原厂 DLL 可选驱动
→ 用户目录中的完整 int32 原始文件
→ 按配置时间段和启用通道直接读取
→ 内存转换 float64
→ 现有 DiagnosisEngine
→ 现有诊断、告警和参数页面
```

本地采集进程仍通过 `127.0.0.1` 上的现有 HTTP 契约接受控制，但完成保存后向本机后端登记原始文件位置，不再上传一份相同波形。远程采集继续上传云端后端副本，两种存储来源在同一个读取边界汇合，上层诊断不复制分支。

每个诊断窗口保留采集记录、起止样本、真实通道号、采样率和启用状态，结果可以追溯至原始文件。窗口进入现有特殊批次语义，不参与普通批次 1～16 循环覆盖。

## 4. 实施任务拆分

### T1：统一波形读取边界

**依赖：无。**

- 将诊断 worker、DataView 和重新诊断对 `SensorData.data` 的直接读取收口到同一读取服务。
- 云端已有数据库数组保持原行为；新增文件来源及时间段读取能力。
- 文件读取返回每通道一维数值数组，读取时转 float64，不保存派生波形。
- 扩展持久化模型以记录文件来源和起止样本，诊断调度、缓存键和查询规则继续共用。
- 本任务不改变算法数学语义，不增加第二套诊断入口。

### T2：增加本地部署配置

**依赖：无，可与 T1 并行。**

- 在统一配置中区分云端与本地工作站，不在视图或业务模块中散布本机地址判断。
- 本地启动强制 `127.0.0.1`，网页、HTTP 和 WebSocket 免登录；云端认证保持原样。
- 同一份前端根据后端提供的部署状态跳过本地登录页，不增加本地前端构建目标。
- 本地初始化只建立实际采集对象，通道数量按有效通道动态变化；云端现有初始化不变。
- 本地页面仍由同一个 `dist/index.html` 提供。

### T3：接通采集记录与完整诊断

**依赖：T1；本地免登录和初始化接入 T2。**

- 采集完成后按配置窗口自动创建诊断批次并入队，沿用现有 worker 和串行信号量。
- 通道启停随采集记录保存；只有启用通道进入分析，原始四路文件不变。
- 重新分析允许选择其他时间段和通道，不重新采集、不复制原始文件。
- 现有 DataView、Diagnosis、Alarm 和参数查看直接消费这些批次，不增加本地专用结果页。
- 已完成的窗口立即持久化并可查询，不等待整份记录分析结束。

### T4：收口三种可选驱动包

**依赖：无；与 T1/T2 并行，但不得改变上层业务契约。**

第一阶段已落地公共 `dc24-driver` 接口以及 `dc24-driver-python` / `dc24-driver-vendor` 独立发行包；单次采集与连续示波共用同一宿主和保存上传逻辑。Rust FFI 阶段已增加 `dc24-driver-rust` 与 `dc24-rust` 组，复用 `dc24_edge_core` 并直接交付完整原始帧；公共接口回环已通过，Windows DC24 实机验收仍未完成。

- 为采集宿主定义窄驱动接口：连接、开始、停止、样本块、帧序号、设备事件和链路状态。
- Python TCP 和原厂 DLL 迁入同一接口；保存、上传、显示和诊断仍由共用宿主负责。
- Rust FFI 复用 `dc24_edge_core`，补齐与共用宿主一致的样本、序号、事件和原始记录能力；不得另写一套 Rust 采集宿主。
- 保留当前 Python TCP 默认路径和原厂 DLL 可选路径，不强制安装原厂软件。
- 根 `pyproject.toml` 和 `uv.lock` 继续统一管理依赖；驱动发行包携带自身构建配置，Rust 编译仍由 cargo 完成。

目标安装形式：

```bash
uv sync --no-default-groups --group local --group dc24-python
uv sync --no-default-groups --group local --group dc24-rust
uv sync --no-default-groups --group local --group dc24-vendor
```

`local` 包含共用应用后端与采集宿主依赖；启动器使用已经选定的环境，不在启动时静默切换驱动。

### T5：更新一键启动与交付说明

**依赖：T2、T3；Rust 启动支持另依赖 T4。**

- `start_dc24.bat` 保留为一键入口，显式选择已安装驱动并打开现有采集页面。
- 本地不依赖 Docker、Nginx 或云服务器；已有前端构建产物时不需要 Node.js。
- 启动过程不要求网页登录，不自动开始采样。
- 更新 DC24 操作、部署、依赖安装和故障说明，明确原始文件是唯一数据源以及移动文件的影响。

**实施结果（2026-11-15）**：本地流式采集关闭文件后以 `finish-stream` 的 `local_directory` 登记实际任务目录，不再逐文件 PUT，也不创建 `data/acquisitions` 副本；任务下载、任务波形和自动诊断均读取该目录的 `counts.i32` 等原件。远程边端保持逐文件上传。启动器从环境或 `dc24/.env` 读取 `DC24_DRIVER=python|rust|vendor`，通过公共 `create_driver` 校验已安装包并取得 transport；`start_dc24.bat` 使用 `uv run --no-sync`，不会自动换回默认驱动。

本轮用临时文件、内存 SQLite、公共接口假驱动和前端测试完成自动回归；未连接真实 DC24 做本地单副本采集验收，Rust Windows 实机采集、停止、保存和诊断仍未验收。

**双轴审查修复结果（2026-11-15）**：统一波形读取已删除 Device/global 运行时采样率兜底，`init_db` 仅为旧 NULL 记录分别物化显示采样率和 `diagnosis_sample_rate_override`；显示保持 origin/main 的统一配置值，诊断保留设备采样率，无法确定时 override 写 0，显示仍可用，`get_diagnosis_sample_rate` 与 reanalyze/worker 明确报错，普通新记录两者相同。Rust 直接实现最小驱动接口，Python/DLL 共享 `FrameProtocolDriver`，无可信接收统计时省略元数据，close 释放资源并传播错误。`load_values` 只接收 ORM job。DataView 原批无参数重诊保持不变，文件批次可选样本/秒区间及 CH1～CH4，复用采集批次分配与窗口登记创建新特殊批次；批次列表提供实际 channels，采集页通道启停同时控制显示与诊断。本地单次任务通过 `/upload?local_directory=...` 复用远程 ZIP 的校验、显示分析和登记流程，不生成 ZIP 或后端副本，缺少 counts 时仅从已校验 CSV 在现场原目录生成。上述自动回归不含实机验收。

### T6：验收与文档收口

**依赖：对应实现任务。**

只保留能证明本次行为改变的验收：

- 原始 int32 与内存 float64 数值一致，未额外归一化，未生成浮点原始副本。
- 窗口起止样本、末段、跨通道采样率及结果追溯正确。
- 仅一路、部分通道和停用后重新启用均能诊断，异常通道不阻塞其他通道。
- 本地断网可完成采集、分析、历史查看；本机无登录页，云端登录和初始化不变。
- 云端既有数据库波形、DataView 和重新诊断行为不变。
- Python、DLL、Rust 驱动经过同一宿主契约检查；Rust 另做 Windows 实机采集、停止、保存和诊断验收。
- 修改 `cloud/app/services/diagnosis/` 或 `cloud/app/algorithms/` 时运行 AGENTS.md 规定的三项 P0 回归；API 变化同步 OpenAPI 并手动调用验证。
- 按文档责任边界更新后端、持久化、API、前后端交互、前端和测试文档，运行 `docs/internal/check_markdown_links.sh`。
