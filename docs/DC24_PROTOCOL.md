## 2. 传输连接：电脑是 TCP 服务端

| 项目 | 本机实测值 |
|---|---|
| 电脑有线 IPv4 | `192.168.2.100` |
| 电脑监听端口 | TCP `6800` |
| 设备 IPv4 | `192.168.2.101` |
| 设备 MAC | `00:08:DC:2B:1A:0C` |
| 连接发起方 | **设备主动连接电脑** |
| 设备 TCP 源端口 | 连接间变化，例如 `6802`、`6809`、`6813`；不要写死 |
| 当前电脑掩码 | `255.255.255.0`，本次使用成功；设备自身掩码没有读出 |

实现应当 `bind(192.168.2.100,6800)` → `listen()` → `accept()`，不是连接设备的 6800 端口。同一时刻，原厂程序和独立脚本不能同时占用电脑的这个监听地址/端口。

未建立上位机连接时，现场曾观测到约 31 秒一次链路断开/重连；建立连接后观察 65 秒没有断连。该现象与连接状态相关，但没有通过固件日志确定内部复位原因。

## 3. 通用帧：TCP 流必须按长度重组

长度不是 TCP 包长度。一次 `recv()` 可能只有半帧，也可能含多帧；采样内容中也可以出现 `7E`，不能靠搜索下一个 `7E` 当作帧尾。

| 偏移，从 0 起 | 字节数 | 含义 |
|---|---:|---|
| 0 | 1 | 帧头 `7E` |
| 1～2 | 2 | `N`，**大端**无符号整数，包含命令字和其后负载，不包含帧头、长度、尾字节 |
| 3 | 1 | 命令/帧类型 |
| 4～N+2 | N−1 | 负载 |
| N+3 | 1 | 控制帧校验或数据帧尾，见下文 |

**总长 = N + 4。** 多字节字段不能一律使用同一种字节序：外层长度大端；已验证的序号、文本长度和配置数值字段为小端。

### 控制帧校验

命令字、负载和尾校验字节的总和低 8 位为 `FF`：

```python
body = bytes([command]) + payload
checksum = (~sum(body)) & 0xff
frame = b'\x7e' + len(body).to_bytes(2, 'big') + body + bytes([checksum])
assert sum(frame[3:]) & 0xff == 0xff
```

### 数据帧尾不是同一校验

原厂采样帧类型 `80` 在本次 62 个帧、两次独立采集的帧中，尾字节均为 `FF`，但整帧不满足控制帧加和规则。当前实现将它作为**实测固定尾字节**检查；没有证据把它称为 CRC。

### 帧外心跳

原厂主机在空闲时约每秒发送一个字节 `00`，它不是 `7E` 帧。独立脚本也每秒发送 `00`，包含等待应答和采集期间。不能只处理采样帧而完全忘记维护连接。

## 4. 控制命令与完整样例

以下空格仅为了阅读，实际发送连续字节。B2/B5 的内容保留原厂本次配置，不能当作所有型号通用默认值。

| 命令 | 本次验证用途 | 主机完整发送帧 | 设备成功应答 |
|---|---|---|---|
| `BA` | 获取设备描述 | `7E 00 01 BA 45` | 可变描述负载，实测完整帧见下 |
| `B8` | 停止 | `7E 00 01 B8 47` | `7E 00 02 B8 00 47` |
| `B2` | 开始前的配置 A，内部字段未确认 | `7E 00 0E B2 00 00 00 00 00 00 00 00 00 01 00 00 00 4C` | `7E 00 02 B2 00 4D` |
| `B5` | 2000 Hz 采集配置 | `7E 00 0D B5 00 00 FE 00 D0 07 00 00 0F 00 00 00 66` | `7E 00 02 B5 00 4A` |
| `B5` | 5000 Hz 采集配置 | `7E 00 0D B5 00 00 F5 00 88 13 00 00 0F 00 00 00 AB` | `7E 00 02 B5 00 4A` |
| `B7` | 本次 F4 实时模式开始 | `7E 00 02 B7 00 48` | `7E 00 02 B7 00 48` |

B2/B5/B7/B8 的实测成功应答都带一个 `00` 负载。脚本只接受这个已验证值；其他状态码的含义未知，不能擅自当成成功。

### BA 设备描述

本设备两次独立采集的应答相同：

```text
7E 00 13 BA 55 00 00 00 00 00 00 00 00 06 00 00 2B 1A 0C FF FF 59 42
```

`13` 表示命令及负载共 19 字节；负载为 18 字节。负载偏移 9 的 `06` 与软件最终报告机号 6 一致；偏移 12～14 的 `2B 1A 0C` 与 MAC 后三字节一致。**这两个对应仅是单台设备的观测，不代表已经完整解出了描述结构。** 其余字段暂不命名。

### 设备主动通知

```text
E0 登录通知：7E 00 0C E0 09 00 4C 61 6E 20 4C 6F 67 69 6E E2
E1 保活通知：7E 00 0B E1 08 00 4C 61 6E 20 4B 65 65 70 56
```

`09 00`/`08 00` 是小端文本长度；文本分别是 ASCII `Lan Login`、`Lan Keep`。在已验证流程里，没有另行构造 E0/E1 应答；维护主机 `00` 心跳即可。

### B2 负载：保留实测原值

```text
00 00 00 00 00 00 00 00 00 01 00 00 00
```

共 13 字节。它发生在停止之后、B5 和开始之前。内部是否对应触发、记录或其他参数，尚未确认；不要仅凭函数命名猜字段。

### B5 负载：两组完整配置与确认程度

```text
2000 Hz：00 00 | FE 00 | D0 07 00 00 | 0F 00 00 00
5000 Hz：00 00 | F5 00 | 88 13 00 00 | 0F 00 00 00
```

| 负载偏移 | 读取方式 | 值 | 确认程度 |
|---|---|---:|---|
| 0～1 | uint16 小端 | 0 | 语义未知，保留原值 |
| 2～3 | uint16 小端 | 254 / 245 | 随 2000/5000 Hz 变化，精确含义未知；两种配置的数据帧仍各有 254 点/通道，故不能解释成直接的每帧点数 |
| 4～7 | uint32 小端 | 2000 / 5000 | 与两次原厂下拉框选择及实际 B5 报文一致 |
| 8～11 | uint32 小端 | 15=`0x0F` | 与启用四通道一致，疑似通道位掩码；未逐位验证 |

上表是第一阶段的两组原厂观测，字段2～3的精确含义仍未知。第二阶段逐档从原厂界面选50～100000Hz抓包，本轮所有B5负载的前4字节均为 `00 00 25 00`，后4字节均为 `0F 00 00 00`，中间4字节为各档采样率。不能把早期FE/F5或本轮25擅自解释成滤波或每帧点数；当前脚本原样采用本轮完整负载。

非标准6000Hz仅作实验时，设备到达速率约6250点/秒；因此用户确认只开放原厂档位。完整抓包在CNN本机忽略目录 `tmp/dc24_live/vendor_rates.*`，本轮实机对照为 `tmp/dc24_live/live_hardware_result.json`。这些路径相对CNN仓库，与下文第一阶段的原始证据根目录不同。

## 5. 可以复现的采集顺序

```text
电脑监听 192.168.2.100:6800
    ↓ 设备主动连入，源端口不固定
维护每秒 00 心跳；解析可能同时到来的 E0/E1
    ↓
BA → 等设备描述
B8 → 等 B8 00 成功应答
B2 + 上述 13 字节 → 等 B2 00
B5 + 上述 12 字节 → 等 B5 00
B7 00 → 等 B7 00
    ↓ 接收并重组 80 数据帧
B8 → 等 B8 00，再关闭连接
```

原厂抓包开始前、停止时曾重复发送 B8；独立脚本单次 B8 加应答等待已经实机验证成功。接收到 TCP 字节不等于收到完整应用帧；状态等待期间也必须继续接收和处理心跳。

## 6. 80 采样帧与四通道计数

早期2000/5000Hz下的采样帧总长 **4071字节**，示例如下。高采样率时帧长会变，不能固定4071：本轮20000Hz实测16263字节、100000Hz实测32519字节。

| 帧偏移 | 字节数 | 内容 |
|---|---:|---|
| 0 | 1 | `7E` |
| 1～2 | 2 | `0F E3`，大端 4067 |
| 3 | 1 | `80` |
| 4～5 | 2 | 帧序号，uint16 小端；每次开始后从 0 起，本次连续递增 |
| 6～4069 | 4064 | 1016 个 4 字节采样项，当前四通道循环排列 |
| 4070 | 1 | `FF`，本次观测到的固定尾字节 |

一个采样项：

```text
第 0 字节：通道标记，本次为 00、01、02、03
第 1～3 字节：小端、有符号 24 位原始 ADC 计数
```

实测标记顺序为 `0,1,2,3,0,1,2,3,...`。通用计算为每通道 `(帧总长-7)/16` 点，先检查负载长度能整除16，再验证各组通道标记。4071字节时每路254点；16263字节时每路1016点；32519字节时每路2032点。16位序号按帧递增而不是按样本递增，回绕按取模处理；本轮短时记录未覆盖长时间回绕。

第一份原厂采集的首帧开头：

```text
7E 0F E3 80 00 00
00 99 06 FB   01 3D 91 F8   02 FA 3E F8   03 D1 D6 F8 ... FF
```

首组四个原始计数分别是 `-325991, -487107, -508166, -469295`。

两种等价的单项解码：

```python
tag = item[0]
counts = int.from_bytes(item[1:4], 'little', signed=True)
# 或者，将整个 4 字节项当成小端 int32，再算术右移 8 位：
counts_again = int.from_bytes(item, 'little', signed=True) >> 8
assert counts == counts_again
```

计数范围是有符号 24 位整数范围。**不应直接把它当成伏特，也不应不经校准就拿 ±10 V 除以 2²³ 来声称是真实电压。** 时间列是样本序号除以本次元数据中的采样率，起点为本次首样本，不是设备 UTC 时间。

7. 本次为兼容性分析，未修改固件、授权文件、原厂程序或加密狗模块。原厂初始化可能自己写运行配置；独立脚本不读写其安装目录。

## 9. 与原厂同一段采集的逐点一致性验证

用户用原厂 F5 采集、F6 停止，并将 DAP/TIM 和导出 CSV 保存在 `D:\1\1\1`。同时被动抓取了同一次设备通信，而不是比较不同时刻分别采集的波形。

证据及可复现脚本：`recordings/comparison_20261105_212358/`；先读其中的 `COMPARISON.md`，详细统计为 `comparison_result.json`，重跑脚本为 `verify_comparison.py`。

- 原始通信：326 个连续数据帧，每通道 82804 点。
- 原厂文件：四路各 69632 点，样本时长 13.9264 秒。
- 原厂保存区间精确对应完整接收流中从 0 计数的 `[8192:77824]`，四路一致；CSV 将该区间起点重新记为时间 0。原厂具体缓存/有效区间机制没有核实，不能仅因文件长度不同就判定漏传。
- 四路 TIM 的全部 278528 个原始 32 位字，与抓包对齐区间逐个相同；右移后的 24 位 ADC 计数也逐个相同。通道标记 0/1/2/3 分别对应软件 6-1/6-2/6-3/6-4。
- 用 DAP `[LevelAndEU]` 的本次换算参数重建后，原厂 CSV 的全部 278528 个数值也逐点相同，最大绝对误差为 0。源文件检查前后 SHA-256 一致。

### 本次可复现的原厂数值换算

本次 DAP 的四路工程单位表均记录偏置字段 0、除数 214741.8125，显示标签为 `m/s^2`。以下计算能在本次记录中全点复现 CSV；它不等于已经独立校准了真实传感器单位。

```python
# counts 是 int32 数组，内容为有符号24位 ADC计数；tag 为该通道的 0/1/2/3。
# 若保留了抓包里的完整32位字，直接使用 packed 即可。
packed = (counts.astype(np.int32) << 8) | np.int32(tag)
value = (packed.astype(np.float64) / 214741.8125).astype(np.float32).astype(np.float64)
# 原厂 CSV 保留5位小数，半入舍入，而非 Python round 的半偶舍入。
export_value = np.sign(value) * np.floor(np.abs(value) * 100000 + 0.5) / 100000
```

低字节的通道标记也保存在原厂 TIM 中；要复现其最后一位导出数值，应保留完整原始字。此公式对应本次偏置为 0 的工程单位配置；不要把本次除数硬套到其他传感器或工程文件。

因此，独立脚本默认的 counts CSV 与原厂工程单位 CSV 直接比较时，数值大小当然不同；**先对齐相同样本，再采用相同换算和导出精度，本次数据完全一致。** 独立脚本当前仍默认保存 counts，未静默改变其输出含义。

## 10. CNN实时页面的上传与绘图约定

设备TCP报文先按前述格式解包，得到每个采样时刻的四个有符号24位计数。边端上传时将这些数放在小端有符号32位整数容器中，不改变数值。请求为 `POST /api/acquisition/sessions/{id}/frames`，查询参数包含 `agent_id`、从零计数的起始样本索引 `start` 和设备帧号 `sequence`；请求体是按时刻排列的二进制数组：`时刻0四路、时刻1四路……`，每个时刻16字节。后端以 `dtype='<i4'`、四列恢复数组，检查24位数值范围；实时上传没有滤波、归一化或回退生成信号。

浏览器从同一会话的 `GET /api/acquisition/sessions/{id}/view` 取得JSON绘图点，每个点为 `[秒数, ADC计数]`。时间由绝对样本索引除以采样率计算。波形默认展开最近0.2秒；频谱使用最近连续、最长2秒的原始窗口。两者窗口用途不同，页面分别说明；较长绘图序列保留极值点，CSV不抽点。各通道独立取列，ECharts采用直线连接，未启用曲线平滑。

2026-11-06在实际Edge页面导出了四张波形、四张频谱的组件数据、ECharts选项和ECharts内部序列，逐点与同会话接口核对一致。另将用户原厂CSV自身分别绘制完整约14秒与其中0.2秒：前者呈密集色块，后者同样呈现规则周期。这是同一文件的显示尺度对照，不是不同采集时刻之间的逐点一致性证明，也不据此作设备或传感器故障判断。

## 12. Windows 原厂 DLL 连接方式

边端配置 `DC24_VENDOR_ROOT` 后，独立 32 位子进程调用已验证的 `JMServer.dll`。DLL 负责本机 TCP 6800 的监听、设备连接与完整帧回调 `0x06`。CNN 仍执行第 5 节的控制顺序，并按第 6 节解析原始计数。

在发送 B7 前，子进程按对端 IP 匹配 DLL 的设备条目，并用 `SetCollectState` 同步内部采集状态。状态未同步时，DLL 会在首帧到达后发出 B8，设备随即停止。网页请求停止后，边端发送 B8 并等待设备成功应答，再关闭本机连接。子进程退出时会对尚未确认停止的采样尝试补发 B8。

所配置的 DLL 必须匹配已验证文件，边端检查 SHA-256 后才加载。`DC24_VENDOR_ROOT` 留空时使用原 Python TCP 实现。保存的原始报文和四路计数格式相同，元数据中的 `transport` 区分连接方式。
